# 🔒 Spring Security & JWT 실습 프로젝트 (`sec-jwt`)

본 프로젝트는 Spring Boot, Spring Security, JPA, Thymeleaf를 활용하여 **무상태(Stateless) 기반의 회원가입, JWT 로그인, 쿠키 기반 사용자 인증**을 구현한 실습 프로젝트입니다.

---

## 🛠️ 기술 스택
- **Framework**: Spring Boot 3.x, Spring Security 6.x
- **Database / ORM**: PostgreSQL, Spring Data JPA
- **Authentication**: JWT (jjwt 0.12.x), Cookie (HttpOnly)
- **Template Engine**: Thymeleaf

---

## 💡 주요 단계별 구현 내용

### 1. 환경 설정 및 프로파일 분리 ⚙️
- **환경 변수 로드 (`.env`):** DB 연결 정보 및 JWT 비밀키와 같은 민감한 데이터는 [`.env`](file:///C:/workspace/sec-jwt/.env) 파일로 격리하여 주입받도록 구성했습니다.
- **설정 프로파일 세분화:** 
  - [`application.yaml`](file:///C:/workspace/sec-jwt/src/main/resources/application.yaml): 기본 설정 정의 및 활성 프로파일 지정 (`dev`, `db`, `auth`)
  - [`application-db.yaml`](file:///C:/workspace/sec-jwt/src/main/resources/application-db.yaml): PostgreSQL 데이터소스 정보 및 JPA/Hibernate DDL/SQL 출력 설정
  - [`application-auth.yaml`](file:///C:/workspace/sec-jwt/src/main/resources/application-auth.yaml): 패스워드 해싱 강도와 JWT 비밀 키(`secret-key`), 토큰 만료 기한(`expiration-ms`) 설정

### 2. JPA Auditing & Base Entity 💾
- 생성일 및 수정일의 자동 기록을 위해 `@CreatedDate`, `@LastModifiedDate`가 선언된 [`BaseEntity.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/common/BaseEntity.java) 클래스를 생성하고 다른 Entity가 이를 상속받도록 설계했습니다.
- Auditing 동작을 위해 별도의 [`JpaConfig.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/common/JpaConfig.java)를 생성하여 `@EnableJpaAuditing`을 활성화했습니다.

### 3. 강화된 패스워드 암호화 (`PasswordEncoder`) 🔐
- 기본 Bcrypt 암호화 방식 외에 보다 보안이 강화된 **Argon2** 방식을 기본으로 사용하도록 BouncyCastle 의존성을 추가했습니다.
- [`SecurityConfig.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/auth/SecurityConfig.java) 내부에서 `PasswordEncoderFactories.createDelegatingPasswordEncoder()`를 통해 여러 해시 알고리즘 지원과 유연한 하위 호환성을 제공하는 `PasswordEncoder` Bean을 구성하고, 기본 인코더로 강력한 `argon2`를 설정했습니다.

### 4. 회원가입 및 DB 연동 👤
- 계정 엔티티인 [`UserAccountEntity.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/user/UserAccountEntity.java)와 [`UserAccountJpaRepository.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/user/UserAccountJpaRepository.java)를 정의했습니다.
- DTO인 [`UserAccountSignUpDTO.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/user/UserAccountSignUpDTO.java)를 입력받아 [`UserAccountService.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/user/UserAccountService.java)에서 비밀번호를 해시화한 후 DB에 저장합니다.

### 5. JWT 기반 로그인 및 무상태(Stateless) 인증 🔑
- **세션 무사용 (Stateless):** REST API 및 확장성 설계를 위해 세션 생성을 하지 않도록 Spring Security를 `SessionCreationPolicy.STATELESS`로 커스터마이징했습니다.
- **JWT 토큰 유틸 구현 (`JwtProvider`):** [`JwtProvider.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/auth/JwtProvider.java)는 `jjwt` 라이브러리를 사용하며 비밀키를 바인딩받아 토큰 생성, 서명 유효성 검증, Claims에서 유저네임(아이디) 추출 작업을 수행합니다.
- **쿠키 발급 (`AuthCookieUtil`):** 로그인 성공 시, 보안 강화를 위해 클라이언트의 LocalStorage 대신 브라우저 자바스크립트가 접근할 수 없는 **HttpOnly, Secure 쿠키** 형태에 JWT를 담아 전달하도록 [`AuthCookieUtil.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/auth/AuthCookieUtil.java)를 설계했습니다.
- **요청 인증 필터 (`JwtFilter`):**
  - [`JwtFilter.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/auth/JwtFilter.java)는 `OncePerRequestFilter`를 확장합니다.
  - 모든 HTTP 요청에 대해 쿠키에서 JWT 토큰을 추출하고, 토큰이 유효한 경우 사용자의 Principal 정보와 권한(Authority)을 담아 `UsernamePasswordAuthenticationToken`을 발급해 `SecurityContextHolder`에 저장합니다.
  - 필터 등록 순서는 `UsernamePasswordAuthenticationFilter` 이전에 수행되도록 Security Filter Chain에 적용했습니다.

### 6. Thymeleaf 템플릿 연동 🖥️
- 실제 프론트엔드 환경에서의 작동을 테스트하기 위해 Thymeleaf 템플릿과 연동 컨트롤러를 구축했습니다.
- [`MyController.java`](file:///C:/workspace/sec-jwt/src/main/java/org/example/secjwt/common/MyController.java):
  - `/` (메인 화면): 로그인 및 회원가입 폼을 보여줍니다. ([`index.html`](file:///C:/workspace/sec-jwt/src/main/resources/templates/index.html))
  - `/my` (마이페이지): JWT 인증 여부를 판단한 뒤, 인증 객체에서 사용자 아이디를 추출해 정보를 화면에 전달합니다. ([`my.html`](file:///C:/workspace/sec-jwt/src/main/resources/templates/my.html))
  - `/logout`: 클라이언트 측의 JWT 쿠키를 만료(MaxAge=0)시켜 세션을 제거합니다.

## 🛠️ 동작 방식 요약 (로그인 & 인증 흐름)

```mermaid
sequenceDiagram
    actor User as 사용자 (브라우저)
    participant Server as 서버 (Spring Boot)
    database DB as 데이터베이스

    Note over User, Server: 1. 로그인 요청
    User->>Server: POST /api/v1/users/login (id, password)
    Server->>DB: 사용자 정보 조회 및 비밀번호(Argon2) 비교
    DB-->>Server: 일치 확인
    Server->>Server: JwtProvider로 JWT Access Token 생성
    Server-->>User: HttpOnly 쿠키(path: '/')에 JWT를 담아 응답

    Note over User, Server: 2. 마이페이지 접근 (인증 필요)
    User->>Server: GET /my (요청 헤더 쿠키에 JWT 자동 포함)
    Server->>Server: JwtFilter 동작 (쿠키의 JWT 추출 및 유효성 검증)
    Server->>Server: 검증 완료 후 SecurityContextHolder에 인증 객체 저장
    Server->>Server: MyController가 인증 객체에서 사용자 정보 추출
    Server-->>User: my.html 페이지 렌더링 (사용자 아이디 노출)
```

## 🚀 실행 및 설정 방법

1. **`.env` 설정**
   - 프로젝트 루트([`C:/workspace/sec-jwt/`](file:///C:/workspace/sec-jwt/)) 디렉토리에 `.env` 파일을 생성하고 데이터베이스 접속 정보와 충분한 길이(최소 256비트 이상)의 JWT 시크릿 키를 정의합니다.
   ```env
   PGHOST=localhost
   PGDATABASE=secjwt
   PGUSER=postgres
   PGPASSWORD=your_password
   JWT_SECRET=your_base64_encoded_secret_key_that_is_long_enough
   ```

2. **애플리케이션 구동**
   ```bash
   ./gradlew bootRun
   ```

3. **브라우저 접속**
   - `http://localhost:8080/` 접속 후 회원가입 -> 로그인 단계를 수행하며 `/my` 마이페이지로 자동 인증 리다이렉트되어 정보가 올바르게 나오는지 검증합니다.

### JWT를 읽는 것과 검증하는 것의 차이

JWT의 payload는 Base64URL로 표현되며 일반적으로 누구나 디코딩할 수 있다. 서명은 내용 변조를 검증하는 수단이지 본문을 숨기는 암호화가 아니다. 서버는 서명·만료와 앱이 요구하는 클레임을 검증한 뒤 인증 객체를 만들어야 한다.

**예시로 이해하기:** 토큰에서 사용자 ID를 읽었다는 이유만으로 인증을 통과시키면 안 된다. Bearer 토큰 추출 → 검증 → SecurityContext 구성 → 인가 순서로 읽는다. 클라이언트가 토큰을 삭제해도 복사된 토큰은 만료 전까지 유효할 수 있어 로그아웃 정책과 별도로 생각해야 한다.

### 토큰 저장 위치와 전송 방식을 분리하기

토큰을 어디에 보관하는지와 요청에 어떻게 실어 보내는지는 별도 선택이다. localStorage는 자바스크립트에서 읽을 수 있어 XSS가 발생하면 토큰도 노출될 수 있다. HttpOnly 쿠키는 직접 읽기를 막지만 XSS 자체나 자동 전송을 이용한 요청까지 모두 막는 것은 아니다.

**예시로 이해하기:** 일반 텍스트 출력은 textContent 또는 템플릿 이스케이프를 사용한다. 401을 받았을 때 인증 갱신이 필요한지 판단하고, 403은 권한 문제로 구분한다. 저장소에서 토큰을 지우는 클라이언트 로그아웃과 서버에서 자격 증명을 무효화하는 일은 다르다.

### 보안 필터의 오류와 컨트롤러 오류

보안 필터에서 차단된 요청은 컨트롤러까지 도달하지 않을 수 있어 ControllerAdvice만으로 모든 오류를 처리할 수 없다. 인증 실패는 AuthenticationEntryPoint, 접근 거부는 AccessDeniedHandler 같은 보안 계층의 처리 지점과 연결한다. 401과 403을 구분해야 클라이언트도 로그인과 권한 부족을 다르게 안내한다.

**예시로 이해하기:** 구체적인 허용 규칙을 앞에 두고 포괄 규칙을 뒤에 두는 순서를 읽는다. JWT 또는 REST라는 이름만으로 CSRF를 꺼도 된다고 판단하지 않는다. 쿠키처럼 브라우저가 자격 증명을 자동 전송하는지와 실제 인증 방식을 기준으로 검토한다.
