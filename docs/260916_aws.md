# 2026-09-16 TIL | AWS 관리형 서비스 연동과 무상태 구조 이해

> EC2 안에 있던 데이터를 외부 서비스로 분리하고, 애플리케이션 서버를 여러 대로 늘리는 구조를 학습했다.

- **실습 환경:** AWS 서울 리전(`ap-northeast-2`), Ubuntu, Docker Compose, Spring Boot, Nginx
- **사용한 서비스:** EC2, RDS MySQL, ElastiCache Redis, S3, ALB

## 오늘 한 일

1. EC2에서 Nginx와 Spring Boot를 Docker Compose로 실행하고 RDS MySQL에 연결했다.
2. EC2와 IntelliJ의 SSH 터널을 통해 RDS·Redis에 접근하는 방식을 실습했다.
3. S3에 객체를 업로드하고 Presigned URL로 다운로드를 확인했다.
4. EC2를 AMI로 복제하고 두 인스턴스를 ALB 대상 그룹에 등록하는 흐름을 실습했다.

## 오늘 배운 핵심

### 1. 서버를 늘리려면 먼저 상태를 어디에 저장할지 정해야 한다

단일 EC2에서 애플리케이션과 DB를 함께 실행할 때는 서버 한 대에 실행 환경과 데이터가 모여 있었다. 이 상태로 서버만 복제하면 각 서버가 서로 다른 데이터를 갖게 될 수 있다.

이번에는 애플리케이션이 사용하는 DB를 RDS로 분리했다. 여러 EC2가 같은 DB를 바라보게 하면서, **애플리케이션 서버의 수명과 데이터의 수명을 분리하는 이유**를 이해했다.

| 서비스 | 학습한 역할 | 이번 실습 범위 |
| --- | --- | --- |
| RDS MySQL | 여러 애플리케이션 서버가 공유하는 DB | Spring Boot의 JDBC 연결 |
| ElastiCache Redis | 공유 캐시·세션 저장소로 활용 | CLI와 SSH 터널을 통한 접속 및 데이터 등록·조회·삭제 |
| S3 | 서버 로컬 디스크와 분리된 객체 저장소 | 테스트 파일 업로드 및 Presigned URL 접근 |
| ALB | 여러 애플리케이션 서버 앞의 요청 진입점 | 두 EC2를 대상 그룹에 등록하고 요청 호출 |

Redis와 S3를 생성했다고 애플리케이션이 자동으로 무상태가 되는 것은 아니다. 현재 `compose.yml`에서 확인할 수 있는 애플리케이션 연동은 RDS이며, Redis 세션 저장이나 S3 파일 업로드 연동은 추가로 구현하고 확인할 부분이다.

```text
클라이언트
    │ HTTP :80
    ▼
   ALB
    ├── EC2 1 → Nginx → Spring Boot ──┐
    └── EC2 2 → Nginx → Spring Boot ──┤
                                     ▼
                                 RDS MySQL

별도 연결 실습
    EC2 / IntelliJ SSH 터널 → ElastiCache Redis
    AWS CLI → S3 업로드 → Presigned URL로 다운로드
```

### 2. 데이터 계층 접근은 보안 그룹을 기준으로 제한한다

RDS와 Redis의 보안 그룹에는 전체 IP 대역 대신 **EC2에 연결된 보안 그룹**을 소스로 지정했다.

```bash
# EC2 보안 그룹을 소스로 지정해 데이터 계층 접근 허용
aws ec2 authorize-security-group-ingress \
  --group-id "$MY_DATA_SG_ID" \
  --protocol tcp --port 3306 \
  --source-group "$MY_SG_ID"

aws ec2 authorize-security-group-ingress \
  --group-id "$MY_DATA_SG_ID" \
  --protocol tcp --port 6379 \
  --source-group "$MY_SG_ID"
```

이렇게 하면 EC2의 개별 IP를 나열하지 않고, 해당 보안 그룹이 연결된 인스턴스의 접근을 허용할 수 있다.

로컬 PC에서는 EC2를 경유하는 SSH 터널로 접속했다. DB를 외부에 공개하는 대신, EC2에서 데이터 계층으로 이어지는 연결 경로를 이용하는 방식이다.

```text
로컬 PC의 IntelliJ → SSH로 EC2 접속 → RDS :3306 / Redis :6379
```

### 3. 로컬 DB를 RDS로 바꿀 때는 Compose의 의존성도 바뀐다

DB 주소만 바꾸면 끝나는 줄 알았지만, 기존 DB 컨테이너를 전제로 한 설정도 함께 수정해야 했다.

- `app`에 남아 있던 `depends_on: db`를 제거했다.
- JDBC URL이 RDS 엔드포인트와 DB 이름을 사용하도록 바꿨다.
- Compose에서 사용하는 변수명을 `.env.rds`와 맞췄다.

핵심 설정은 다음과 같다. 전체 구성은 [compose.yml](https://github.com/pjmoo/260916_aws/blob/main/compose.yml)에 기록했다.

```yaml
# services.app 설정 중 일부
  env_file:
    - .env.rds
  environment:
    SPRING_DATASOURCE_URL: "jdbc:mysql://${RDS_ENDPOINT}:3306/${DB_NAME}?createDatabaseIfNotExist=true"
    SPRING_DATASOURCE_USERNAME: ${DB_USER}
    SPRING_DATASOURCE_PASSWORD: ${DB_PASSWORD}
```

```bash
# EC2의 프로젝트 디렉터리에서 실행
sudo docker compose --env-file .env.rds config
sudo docker compose --env-file .env.rds up -d --remove-orphans
curl -i http://localhost/
```

이번 실행에서는 `--env-file .env.rds`로 Compose의 `${...}` 치환에 사용할 값을 지정했다. 서비스의 `env_file`은 컨테이너에 전달할 환경 변수를 지정하는 설정이므로 두 용도를 구분해서 기억해야겠다.

### 4. S3 객체는 버킷을 공개하지 않고도 공유할 수 있다

S3에 테스트 파일을 올리고, 유효 시간을 300초로 설정한 Presigned URL을 발급했다.

```bash
aws s3 cp hello.txt "s3://$MY_BUCKET/hello.txt"
aws s3 presign "s3://$MY_BUCKET/hello.txt" --expires-in 300
```

버킷 전체를 공개하는 대신 특정 객체에 대한 임시 접근 권한을 전달하는 방법을 배웠다. 발급된 URL을 가진 사람이 사용할 수 있으므로 URL 자체도 공유 범위를 신경 써야 한다.

### 5. AMI 복제와 ALB 연결은 서로 다른 역할이다

AMI는 실행 환경을 복제하는 데 사용했고, ALB는 복제한 서버들을 하나의 진입점으로 묶는 데 사용했다.

실습 흐름은 **AMI 생성 → 두 번째 EC2 실행 → 대상 그룹 등록 → ALB 리스너 연결 → DNS 주소로 요청** 순서였다.

ALB 주소에 요청을 보냈다는 사실만으로 두 서버가 모두 처리했다고 단정할 수는 없다. 실제 요청 분산 여부는 서버별 응답 메시지나 로그를 함께 확인해야 알 수 있다.

## 겪었던 문제와 해결

### `ParameterNotFound`: 복사한 명령어의 줄바꿈 확인

- **상황:** Ubuntu AMI ID를 조회하는 `aws ssm get-parameter` 명령에서 오류가 발생했다.
- **원인으로 정리한 내용:** 여러 줄의 Bash 명령어를 복사하는 과정에서 줄 끝의 공백이나 Windows 줄바꿈 문자(`CRLF`)가 섞였다.
- **해결:** 명령을 한 줄로 정리해 다시 실행했다.
- **배운 점:** 경로가 맞아 보이더라도 실제 전달되는 문자열과 실행 셸을 확인해야 한다. 여러 줄 명령에서 `\` 뒤에 공백이 없는지도 확인해야 한다.

### `Permission denied`: 읽기 전용 개인키 파일 덮어쓰기

- **상황:** 키 페어를 다시 생성하면서 기존 `.pem` 파일에 출력하려고 하자 실패했다.
- **원인:** 앞서 `chmod 400`을 적용해 파일에 쓰기 권한이 없었다.
- **해결:** 실습에서는 기존 파일을 삭제한 뒤 새로 생성했다.
- **배운 점:** AWS API 오류와 로컬 파일 쓰기 오류는 구분해야 한다. 키를 재생성할 때는 기존 키가 필요한 인스턴스가 있는지도 먼저 확인해야 한다.

### `depends on undefined service "db"`: 남아 있는 로컬 DB 의존성

- **상황:** `docker compose ... config` 실행 시 유효성 검사가 실패했다.
- **원인:** 로컬 `db` 서비스를 제거했지만 `app`의 `depends_on: db`가 남아 있었다.
- **해결:** 해당 의존성을 제거하고 DB 연결 변수명을 `.env.rds`와 맞췄다.
- **배운 점:** 외부 서비스로 이전할 때는 연결 주소뿐 아니라 기존 서비스에 대한 의존성도 확인해야 한다.

### `502 Bad Gateway`: 실제 원인은 DB 연결 실패

- **상황:** 웹에서는 Nginx의 `502 Bad Gateway`가 보였고, Spring Boot 컨테이너는 재시작을 반복했다.
- **원인:** RDS 인스턴스는 생성됐지만 애플리케이션이 사용할 `appdb`가 없어 `Unknown database 'appdb'`가 발생했다.
- **해결:** 실습에서는 JDBC URL에 `createDatabaseIfNotExist=true`를 추가했다.
- **배운 점:** RDS 인스턴스 생성과 애플리케이션용 DB 생성은 별개다. 프록시에서 보이는 오류만 보지 말고 애플리케이션 로그까지 따라가야 원인을 찾을 수 있다.

## 오늘 배운 점

오늘 가장 크게 배운 것은 **관리형 서비스로 옮기는 작업이 연결 주소 변경만으로 끝나지 않는다는 점**이다. Compose 의존성, 환경 변수, DB 생성 여부, 보안 그룹까지 서로 맞아야 애플리케이션이 동작했다.

특히 `502`의 원인이 Nginx 설정이 아니라 DB 연결 실패였던 경험이 기억에 남는다. 오류가 보이는 위치와 실제 원인이 있는 위치를 구분하고, 요청이 지나가는 순서대로 확인하는 것이 중요하다는 점을 배웠다.

또한 이번 구성의 RDS는 `--no-multi-az`, Redis는 단일 노드로 생성했다. 여러 가용 영역의 서브넷을 그룹에 넣은 것과 데이터 계층의 고가용성을 구성한 것은 구분해서 이해해야 한다.
